## 二、通用回答思路

### 1. 技术原理题：五段式

推荐结构：

> 结论 -> 核心原理 -> 钱包场景 -> 风险边界 -> 一句话总结

示例题：“Redis 分布式锁能否保证提币不重复？”

1. **结论**：不能单独保证，只能作为并发优化手段。
2. **原理**：锁可能因超时、主从切换、网络分区或进程停顿而失效。
3. **生产实现**：数据库业务单唯一键、状态迁移条件、链资源唯一约束承担最终正确性，Redis 只减少竞争。
4. **风险边界**：签名后崩溃、广播结果未知时不能直接创建新交易，必须先查询原交易。
5. **总结**：缓存和锁提高效率，数据库约束与链上核验守住资金正确性。

### 2. 流程设计题：状态机六问

回答充值、提币、归集等流程时，依次说明：

1. 输入从哪里来，信任边界在哪里？
2. 正常状态如何流转？
3. 业务唯一键和链上唯一标识是什么？
4. 每次状态迁移的前置条件是什么？
5. 超时、重复、乱序、重启、重组如何恢复？
6. 如何监控、对账、审计和人工兜底？

#### 充值流程参考答案

**1. 输入与信任边界**

充值流程的输入来自链上区块、交易、Receipt 或 Event Log，由扫链服务通过自建节点或第三方 RPC 获取。地址服务提供交易所地址与用户、Memo、资产之间的绑定关系，资产配置中心提供支持的链、Token 合约、精度、最小充值额和确认策略。

节点数据属于外部输入，不能直接信任。系统需要校验网络与 Chain ID、区块高度和哈希连续性、交易执行结果、目标地址、Memo、Token 官方合约、金额和资产精度。重要数据可以通过多个节点交叉验证。地址映射、资产白名单和账本属于内部高信任数据，但配置变更也必须经过审批、版本管理和审计。

**2. 正常状态流转**

```text
未发现 -> 已发现 -> 待确认 -> 已确认 -> 已入账
                         |          |
                         v          v
                      已作废      已冲正/人工处理
```

1. 扫链服务按高度拉取区块，识别属于交易所的原生币转账或 Token 事件。
2. 校验资产、地址、Memo、执行结果和金额后，幂等创建“已发现”充值记录。
3. 记录所在区块高度和哈希，进入“待确认”，持续计算确认数或检查链的最终性标签。
4. 达到按链、资产、金额和风险配置的确认条件后，条件更新为“已确认”。
5. 在一个本地事务中写入不可变账本分录、更新充值为“已入账”、写入 Outbox。
6. Outbox 发布到账通知；后续归集由独立流程处理，不阻塞用户入账。

**3. 业务唯一键与链上唯一标识**

| 场景 | 推荐链上唯一标识 |
|---|---|
| BTC 充值 | `chainId + txid + vout` |
| EVM 原生币充值 | `chainId + txHash + 接收地址`，若系统支持内部调用还需加入 trace 标识 |
| ERC-20 充值 | `chainId + txHash + logIndex` |
| Solana 充值 | `cluster + signature + instructionIndex/innerInstructionIndex + 账户或 Mint` |
| TON/Jetton 充值 | `workchain + transactionHash/LT + messageHash`，并结合 Memo 或消息索引 |

内部可以生成 `depositId` 作为业务主键，但它不能替代链上唯一约束。账本分录还应以 `depositId + entryType` 建立唯一约束，确保同一充值只入账一次。具体键应根据所用节点 API 能否稳定返回内部调用或消息索引进行确认，不能只用 `txHash`，因为一笔交易可能包含多笔 Token 转账或多个输出。

**4. 状态迁移前置条件**

| 状态迁移 | 必须满足的条件 |
|---|---|
| 未发现 -> 已发现 | 链和资产受支持；地址/Memo 归属明确；链上标识唯一；金额大于零；交易或事件格式合法 |
| 已发现 -> 待确认 | 区块位于当前规范链；已保存区块高度、区块哈希和交易位置；交易执行语义有效 |
| 待确认 -> 已确认 | 当前规范链仍包含该交易；确认数或最终性达标；未命中高风险冻结规则 |
| 已确认 -> 已入账 | 充值状态仍为已确认；账本中不存在同一 `depositId` 分录；用户和资产账户有效；数据库事务可完整提交 |
| 已入账 -> 已冲正 | 有重组或错误入账证据；经过风险策略或人工审批；通过冲正分录处理，不删除原流水 |

状态更新使用类似 `UPDATE ... WHERE id=? AND status=? AND version=?` 的条件更新，避免重复消费者或乱序消息越级推进。

**5. 异常恢复**

- **超时**：RPC 超时不移动扫描游标；切换节点或重试同一高度。账本事务超时按结果未知处理，先查询数据库，不直接再次入账。
- **重复**：允许区块和消息重复处理，由链上唯一索引、账本唯一键和条件状态迁移拦截。
- **乱序**：状态机只允许合法前向迁移；同链区块游标按顺序提交，较晚到达的旧消息只能补充信息，不能覆盖新状态。
- **重启**：扫描器从最后一个已提交的安全检查点前若干块重新扫描；未完成任务由状态表或 Outbox 恢复，不依赖进程内存。
- **重组**：通过高度、区块哈希和父哈希发现分叉，回退到共同祖先。未入账记录退回待确认或作废；已入账记录写冲正分录，必要时冻结用户余额和提币，交易重新上链后重新确认。
- **漏扫**：定时按高度区间重扫，并用节点记录、充值表、账本分录三方对账发现缺口；历史重扫使用独立限流队列，避免影响实时扫描。

**6. 监控、对账、审计与人工兜底**

- 监控链头高度、已扫描高度及差值、单块处理耗时、RPC 错误率、待确认时长、入账延迟、重组深度、重复命中数和失败状态数量。
- 对账比较链上充值事件、充值业务记录和账本分录，检查“链上有但业务无、业务有但账本无、金额或资产不一致”。
- 审计保留原始交易标识、区块信息、解析器版本、资产配置版本、每次状态变更、账本凭证和操作人；敏感用户信息按权限展示。
- 对漏填 Memo、非标准 Token、深度重组、金额不一致等异常进入人工工单。人工只能执行预定义的重扫、重新关联、冲正或补账动作，必须双人复核，不能直接修改余额和历史流水。

**面试口述版**：

> 充值的输入来自节点和链上数据，所以首先把 RPC 当作不可信边界，校验链、区块连续性、交易结果、地址或 Memo 归属以及 Token 合约白名单。正常流程是已发现、待确认、已确认、已入账；达到确认条件后，在同一数据库事务里写账本、改状态和写 Outbox。幂等不能只靠程序判断，BTC 用 `txid + vout`，ERC-20 用 `txHash + logIndex` 等链上标识建立唯一索引，账本再按业务单唯一。超时不代表失败，重复扫描是允许的；重启后从安全检查点回扫，重组则回退到共同祖先，已入账资金通过冲正和冻结处理。最后用扫描高度差、到账延迟和三方对账监控正确性，复杂异常走有审批和审计的人工流程。

#### 提币流程参考答案

**1. 输入与信任边界**

提币输入主要来自用户/API 的提币申请，包括业务请求号、用户、链、资产、金额、目标地址、Memo/Tag 和认证信息；还包括账户账本余额、KYC/AML 结果、地址白名单、手续费配置、节点状态及审批结果。

用户输入、目标地址、前端传入的网络和 Memo 都不可信，必须在服务端重新校验。第三方 AML 和节点响应也属于外部边界，应设置超时、结果签名或来源认证，并采取保守降级。提币服务本身不能被签名服务完全信任；签名服务必须独立解析交易，核对审批单、地址、金额、手续费、合约和链资源。私钥边界位于 HSM、KMS 或 MPC 系统内，任何业务服务都不应获取明文私钥。

**2. 正常状态流转**

```text
已申请 -> 已冻结 -> 风控/审核通过 -> 构建中 -> 待签名
   |          |              |                         |
   v          v              v                         v
已拒绝     已取消         构建失败                 已签名
                                                       |
                                                       v
                                             已广播/结果未知
                                                       |
                                                       v
                                                已确认 -> 已完成
```

1. 幂等接收申请，校验用户、地址、网络、资产、金额、限额和账户状态。
2. 在账本事务中把金额及预计费用从可用余额转为冻结余额。
3. 执行 KYC/AML、设备风险、地址白名单、速度和额度规则，必要时人工审核。
4. 分配并持久化链特有资源：BTC UTXO、EVM nonce、Solana Blockhash 相关交易上下文、TON `seqno`。
5. 构建确定的交易内容，将业务单、审批结果和交易摘要提交独立签名服务。
6. 保存签名原文、预期交易哈希后广播；广播结果未知时进入独立状态。
7. 跟踪链上状态，达到确认条件后将冻结余额结转为最终扣减，记录手续费并完成业务单。

**3. 业务唯一键与链上唯一标识**

- 业务唯一键优先使用调用方生成且不可复用的 `clientRequestId`，平台内部再生成全局唯一 `withdrawalId`。
- 冻结、正式扣减、解冻等账本操作分别使用 `withdrawalId + entryType` 唯一约束。
- 签名请求使用 `withdrawalId + transactionVersion + payloadHash` 唯一约束，防止旧版本或篡改内容被签名。
- 广播前保存确定的交易哈希或签名。EVM 还应唯一约束 `chainId + fromAddress + nonce`；BTC 唯一约束每个已预占 UTXO；TON 约束 `wallet + seqno`。
- 交易替换不能覆盖历史记录，应由原交易和替换交易形成关联链，并明确当前有效版本。

**4. 状态迁移前置条件**

| 状态迁移 | 必须满足的条件 |
|---|---|
| 已申请 -> 已冻结 | 请求幂等校验通过；账户可用；可用余额充足；未触发账户级禁止条件 |
| 已冻结 -> 审核通过 | KYC/AML、地址、限额、设备与人工规则均通过；风控结果仍在有效期内 |
| 审核通过 -> 待签名 | 链状态可用；费用合理；链资源原子分配成功；交易构建和模拟通过 |
| 待签名 -> 已签名 | 审批未过期；交易摘要与审批内容一致；签名策略通过；签名结果本地验签成功 |
| 已签名 -> 已广播 | 原始交易和预期哈希已持久化；广播操作针对同一签名原文；没有暂停开关 |
| 已广播 -> 已确认 | 交易位于规范链；执行成功；确认数或最终性达标；实际转账资产和金额符合预期 |
| 已确认 -> 已完成 | 最终账本扣减和手续费分录成功；状态更新与 Outbox 在同一事务中提交 |
| 冻结 -> 解冻/取消 | 尚未进入不可逆链上阶段，或已证明所有交易版本都不可能生效；经过条件更新和授权 |

**5. 异常恢复**

- **超时**：签名或广播超时进入“结果未知”，按业务单、payload hash、交易哈希和链资源查询。不能直接换 nonce、UTXO 或重新构建。
- **重复**：重复申请返回原业务结果；重复签名请求只允许返回同一 payload 的既有结果；重复广播同一原始交易通常是幂等的。
- **乱序**：消息携带业务版本，数据库按当前状态和版本条件更新。例如“已确认”先到时可主动回查链上并补齐状态，旧的“已广播”消息不得把状态回退。
- **重启**：从数据库扫描长时间停留在构建中、待签名、结果未知、已广播的任务，分别查询资源、签名和链上事实后恢复；不能依赖 Redis 锁或内存队列还原正确性。
- **重组**：确认前交易被移除时退回广播跟踪状态；已完成后发生极深重组，应冻结风险账户、重新判断交易是否进入新规范链，并通过账本补偿处理，不能删除原扣款。
- **卡链**：BTC 根据条件使用 RBF/CPFP，EVM 使用相同 nonce 提价替换，Solana 先确认旧签名失效再换 Blockhash 重签，TON 核对 `seqno` 和消息链后处理。
- **永久失败**：仅在证明交易未生效且链资源可安全释放时解冻；已支付的链上手续费单独记账。

**6. 监控、对账、审计与人工兜底**

- 监控各状态数量和停留时间、风控拒绝率、签名延迟、广播成功率、结果未知数量、确认时长、链资源冲突、失败原因和热钱包余额。
- 对账比较提币业务单、账本冻结/扣减、签名记录、广播记录和链上实际交易，重点发现“扣款未上链、上链未扣款、金额/地址不一致、一个业务单多笔有效交易”。
- 审计记录请求来源、认证和风控结果、审批人、配置版本、交易解析结果、签名密钥版本、广播节点及所有状态变化，但不记录私钥或敏感认证凭据。
- 高额、命中风险、长期结果未知、交易参数不一致和疑似重复支付必须进入人工工单。人工操作采用双人复核、限权命令和完整审计，广播后不得简单点击“失败并退款”。

**面试口述版**：

> 提币以用户请求为输入，但地址、网络、Memo、AML 和节点结果都不能直接信任。正常流程是申请、冻结、风控审批、构建、签名、广播、确认和完成。业务单号保证请求幂等，账本按业务单和分录类型唯一；链上还要锁定 UTXO、nonce 或 `seqno`，签名请求则绑定业务单和 payload hash。每次状态变化都使用当前状态加版本的条件更新，签名前校验审批和交易内容，完成前核验链上执行与账本扣减。广播超时属于未知而非失败，先查原交易，再决定同原文重播或链特定替换。系统监控状态停留和未知结果，并把业务、账本、签名、广播与链上交易做五方对账；高额或不确定操作必须人工双审。

#### 归集流程参考答案

**1. 输入与信任边界**

归集不是用户直接请求，而是资金调度系统根据充值地址余额、资产配置、归集阈值、网络费用、热钱包水位和风险策略生成任务。输入来自扫链余额、节点查询、地址归属表、资产合约白名单和费用估算。

节点余额和费用报价属于外部输入，需要校验区块新鲜度并可由多节点复核；任何“待归集地址”必须从受控地址库反查，不能接受调用方随意传入私钥或源地址。目标归集地址必须来自审批后的白名单配置。Gas 补充服务和归集服务相互不应无限信任，补充额度、频率和可归集 Token 必须受策略限制。

**2. 正常状态流转**

```text
候选发现 -> 已计划 -> 资源准备 -> 待签名 -> 已广播 -> 已确认 -> 已完成
                |           |
                v           v
              已跳过      等待 Gas/账户准备
```

1. 定时或事件驱动发现余额达到阈值的受控地址，创建候选记录。
2. 根据链费、最小保留余额、Token 价值、风险和批次上限生成归集计划。
3. 准备链特有资源：BTC 选择 UTXO；ERC-20 必要时定额补充 Gas；SPL Token 检查目标 ATA；TON/Jetton 检查消息费用。
4. 原子预占地址、UTXO、nonce 或批次资源，构建并模拟交易。
5. 签名服务校验源地址归属、目标白名单、金额、费用和批次策略后签名。
6. 广播并跟踪确认；确认后更新地址可归集余额、任务状态和资金调度记录。
7. 对归集结果与链上余额进行核对，释放资源并结束批次。

**3. 业务唯一键与链上唯一标识**

- 使用 `collectionTaskId` 作为内部任务主键，并通过 `chain + asset + sourceAddress + balanceSnapshot/planVersion` 防止同一余额快照重复生成有效任务。
- Gas 补充任务使用 `collectionTaskId + sourceAddress + gasTopupVersion` 唯一约束，并设置累计补充上限。
- BTC 对每个 UTXO 建立唯一占用；EVM 对 `fromAddress + nonce` 建立唯一约束；TON 对 `wallet + seqno` 唯一约束。
- 链上唯一标识与提币类似，使用交易哈希；批量 BTC 归集还要记录每个输入 UTXO，Token 归集要记录对应 Event/Instruction/Message 标识。
- 一次旧计划失败后重新规划必须增加版本，并关联原任务，不能覆盖旧签名或广播记录。

**4. 状态迁移前置条件**

| 状态迁移 | 必须满足的条件 |
|---|---|
| 候选发现 -> 已计划 | 地址属于交易所；资产受支持；余额达到阈值；扣除费用后仍有归集价值；不存在有效归集任务 |
| 已计划 -> 资源准备 | 目标地址在白名单；批次限额通过；链和节点健康；余额快照未发生不允许的变化 |
| 资源准备 -> 待签名 | Gas/ATA/UTXO/nonce 等条件满足；资源预占成功；交易模拟通过；费用未超过上限 |
| 待签名 -> 已广播 | 签名策略通过；本地验签成功；原文和交易哈希已持久化；未触发暂停开关 |
| 已广播 -> 已确认 | 交易在规范链执行成功并达到确认标准；目标地址和实际到账金额符合预期 |
| 已确认 -> 已完成 | 源地址、目标地址和费用已完成链上对账；批次记录与资金调度记录已更新 |

**5. 异常恢复**

- **超时/重复/重启**：采用与提币相同的“结果未知”原则和确定交易哈希恢复；任务、资源占用和签名原文全部持久化，调度器重启后按状态继续。
- **余额变化**：构建前重新查询余额；若充值又进入源地址，可留待下一批，不临时扩大已审批交易金额。账户模型链还要预留手续费。
- **Gas 补充失败**：限制单地址单次、每日及全局补充额度；只给已确认有受支持 Token 且达到归集价值的地址补充；补充后仍无法归集则停止自动重试并告警，避免无限循环。
- **资源冲突**：BTC UTXO 已被消费则废弃旧计划并重新选币；EVM nonce 冲突先恢复该地址的 nonce 队列；Solana Blockhash 过期先核验旧签名；TON 核对 `seqno` 和消息状态。
- **重组**：确认前回到跟踪或重播状态；归集确认后发生深度重组时重新核对源、目标余额和交易状态，再决定重播或重新规划。
- **费用突增**：超过配置上限时暂停或延后低价值归集，不因重试无上限提高费用。

**6. 监控、对账、审计与人工兜底**

- 监控待归集资产价值、地址数量、任务成功率、状态停留时间、单笔/单位资产成本、Gas 补充成功率、热钱包和冷钱包水位、失败重试次数。
- 对账比较归集计划、资源占用、Gas 补充、签名和广播记录、源地址减少额、目标地址增加额及实际手续费。
- 审计保留触发规则、余额快照、计划版本、目标白名单版本、费用估算、审批、签名和交易结果，确保能回答“为什么归集、归集到哪里、花了多少费用”。
- 对高额归集、目标地址变更、连续 Gas 补充失败、源目标差额异常、长期未知交易进入人工处理。冷转热和大额热转冷通常需要多方审批或离线流程，不应完全自动化。

**面试口述版**：

> 归集由资金调度系统根据受控地址余额、阈值、链费和钱包水位触发，不接受外部随意指定源地址或目标地址。流程是候选发现、生成计划、准备 Gas 或链资源、构建签名、广播确认和对账完成。内部用任务号和余额快照防止重复计划，链上用 UTXO、nonce、`seqno` 等唯一资源防止并发冲突。每步都要求地址归属、目标白名单、成本上限和资源状态满足条件。异常时保留原交易先查链上事实；ERC-20 Gas 补充必须有单次和累计上限，避免被恶意地址消耗；费用过高时低价值归集可以延后。最后监控待归集资产、成本、状态停留和冷热水位，并核对源地址减少、目标地址增加和实际手续费，大额调度采用多方审批。

### 3. 系统设计题：八步法

1. **澄清需求**：支持哪些链和资产，充值/提币量级，安全等级，确认时效，合规要求。
2. **定义目标**：资金正确性优先，其次是安全、可恢复性、可用性和效率。
3. **划分模块**：节点网关、链适配、地址、扫描、充值、提币、归集、签名、账本、对账、风控。
4. **讲主流程**：先讲充值和提币两条主链路，不从技术组件堆砌开始。
5. **讲数据**：核心表、唯一键、状态机、金额类型和审计字段。
6. **讲一致性**：本地事务、Outbox、消费幂等、链资源锁和补偿。
7. **讲安全与容灾**：冷热分层、签名隔离、限额、多节点、暂停开关和恢复流程。
8. **讲观测与验证**：高度差、处理延迟、广播/确认率、余额水位、对账差异和故障演练。

### 4. 故障题：时间线法

> 先止损 -> 确认影响 -> 保全证据 -> 恢复一致性 -> 分批恢复 -> 复盘改进

不要一上来就“重启”或“重试”。资金系统先判断操作是否已经产生链上效果，再决定补偿动作。

### 5. 项目经历题：STAR + 复盘

- **S（背景）**：业务规模、原有问题、约束条件。
- **T（任务）**：你的职责和可衡量目标。
- **A（行动）**：你亲自完成的设计、实现、协作和取舍。
- **R（结果）**：延迟、吞吐、故障率、恢复时间或资金差异等数据。
- **复盘**：方案局限、后续改进，以及当时为什么没有选择另一方案。

当缺少直接钱包经验时，可以这样表达：

> 我没有把个人实践包装成生产经验。我的可迁移能力来自 Java 分布式系统中的幂等、一致性、状态机、审计和故障恢复；同时我已针对 BTC、EVM、Solana、TON 分别完成交易解析和钱包流程设计。我会明确哪些结论经过实践验证，哪些仍需要在真实业务量和安全流程下验证。

## 三、高频问题与参考答案

### 1. 交易所托管钱包和 MetaMask 有什么本质区别？

**回答思路**：密钥归属 -> 余额来源 -> 服务对象 -> 风险责任。

**参考答案**：

本质区别是资产控制权和账务模型。MetaMask 属于自托管钱包，私钥由用户持有，余额主要来自链上地址状态；交易所托管钱包由平台控制密钥，面向大量用户统一管理资金。用户看到的余额来自交易所内部账本，并不等于某个充值地址的链上余额。托管系统还必须处理地址分配、扫链、充值确认、提币审批、归集、冷热调度、签名隔离、对账和合规，因此其核心挑战不仅是“发一笔链上交易”，而是安全地维护链上资产与内部负债的一致性。

### 2. 如何保证充值不重不漏？

**回答思路**：扫描游标 -> 业务唯一键 -> 状态机 -> 重组 -> 重扫与对账。

**参考答案**：

我会采用“至少一次扫描 + 幂等入账”，而不是依赖扫描只执行一次。扫描器按区块高度推进，同时保存区块哈希，用父块关系检测重组。充值记录使用链上稳定标识建立唯一约束，例如 BTC 使用 `txid + vout`，EVM Token 使用 `chainId + txHash + logIndex`。发现充值后先进入待确认状态，达到按链、资产、金额和风险配置的确认条件后，在同一数据库事务中写入账本分录、更新充值状态并写 Outbox。重复消息由唯一索引和状态迁移条件拦截。系统还要支持历史重扫、扫描高度差监控、链上与内部账本对账；发生重组时将受影响记录回退，必要时冻结相关余额并进入人工处理。

### 3. 已经入账的充值发生链重组怎么办？

**回答思路**：检测 -> 标记影响 -> 逆向账务 -> 风险控制 -> 重新确认。

**参考答案**：

扫描器通过已保存区块哈希与当前规范链比较发现重组，找到共同祖先后回退受影响区块。尚未入账的充值退回待确认或作废；已入账的充值不能直接删除流水，而应写冲正分录并保留完整审计记录。如果用户已使用这笔余额，应冻结账户可用余额、阻断相关提币，并按负余额或人工审核流程处理。若交易重新出现在规范链上，则按新的区块位置重新累计确认。大额充值采用更高确认数，是降低这种损失概率的手段，但不能替代重组处理机制。

### 4. 如何保证提币不重复？

**回答思路**：请求层 -> 账本层 -> 链资源层 -> 签名层 -> 广播未知结果。

**参考答案**：

提币需要多层幂等。请求层使用用户请求号或平台业务单号唯一约束；账本层在事务中冻结余额，确保同一业务单只冻结一次；构建层锁定链特有资源，例如 BTC 的 UTXO、EVM 的 nonce、TON 的 `seqno`。签名请求绑定业务单、交易摘要和策略版本，签名服务拒绝重复或不符合审批结果的请求。广播可以重复发送同一份已签名原始交易，因为其交易哈希不变，但广播超时后绝不能直接构建新交易，必须先按原交易哈希、nonce、UTXO 等查询链上和节点状态。最终通过状态机条件更新、唯一约束和链上对账收敛。

### 5. 提币余额应该何时扣减？

**回答思路**：可用余额与所有权语义 -> 冻结 -> 最终扣减/解冻。

**参考答案**：

用户提交并通过基础校验后，应先将金额和预计手续费从可用余额转为冻结余额，防止重复消费；不能等到链上确认才控制余额。提币进入不可逆阶段后，根据账务规则把冻结余额正式扣减；若在签名前被拒绝或安全取消，则解冻。广播后结果未知不能轻易解冻，因为交易可能已经进入网络。具体“正式扣减”发生在广播还是确认可以由业务会计政策决定，但状态必须能表达在途资金，并保证账本分录不可变、可审计、可补偿。

### 6. 广播请求超时后怎么处理？

**回答思路**：未知不等于失败 -> 保留原交易 -> 多维查询 -> 同原文重播或链特定替换。

**参考答案**：

超时只表示客户端不知道结果，不表示节点没有接收。系统应把任务标记为“广播结果未知”，保留完整已签名交易和预期哈希，先向多个节点查询交易、Mempool 和链上资源状态。查到原交易就继续跟踪；暂时查不到时，可以幂等地重播同一原始交易。只有确认原交易未生效且满足链特定条件，才允许重建或替换，例如 EVM 使用相同 nonce 和更高费用替换，BTC 使用 RBF 或 CPFP。任何新建动作都需要审计和防双付检查。

### 7. BTC UTXO 与 EVM nonce 的并发控制有什么不同？

**回答思路**：冲突资源 -> 锁定方式 -> 失败影响 -> 恢复。

**参考答案**：

BTC 的冲突资源是离散 UTXO。同一个 UTXO 只能被一笔确认交易消费，因此构建时要在数据库中原子预占，并在失败或过期后按状态释放；不同 UTXO 可以并行。EVM 同一发送地址的交易按 nonce 排序，分配重复 nonce 会产生替换竞争，出现 nonce gap 又会阻塞后续交易，因此通常由持久化 nonce 管理器串行分配，数据库锁和唯一约束负责正确性。恢复时 BTC 核对 UTXO 是否已花费，EVM 则同时比较 confirmed nonce、pending 交易和本地分配记录。

### 8. EIP-1559 手续费如何计算？

**回答思路**：上限字段 -> 实际单价 -> 总费用 -> 退款语义。

**参考答案**：

用户设置 `maxFeePerGas` 和 `maxPriorityFeePerGas`。实际单价通常为：

$$
\text{effectiveGasPrice}=\min(\text{maxFeePerGas},\ \text{baseFee}+\text{maxPriorityFeePerGas})
$$

实际费用为：

$$
\text{fee}=\text{gasUsed}\times\text{effectiveGasPrice}
$$

`baseFee` 被销毁，小费给出块者。`gasLimit` 是最多允许消耗的 Gas，不是一定收取的数量；未使用部分不会按上限收费，但交易执行失败通常仍要支付已经消耗的 Gas。

### 9. ERC-20 充值为什么不能只看交易的 `to` 和 `value`？

**回答思路**：外层交易 -> 合约执行 -> Event Log -> 非标准代币。

**参考答案**：

ERC-20 转账时，外层交易的 `to` 通常是 Token 合约地址，`value` 通常为零，真正的收款地址和数量位于调用数据及执行结果中。充值识别应校验链、官方 Token 合约地址、成功 Receipt，并解析标准 `Transfer` Event 的 `from`、`to` 和 `value`，唯一键通常包含 `txHash + logIndex`。还要考虑代理合约、内部调用、手续费代币、Rebase 及非标准事件，所以资产接入前必须建立白名单和专项解析测试，不能仅凭代币名称或符号识别。

### 10. Solana 的 Recent Blockhash 有什么作用？

**回答思路**：新鲜度与防重放 -> 有效窗口 -> 过期恢复 -> 重复支付风险。

**参考答案**：

Recent Blockhash 让交易只在有限窗口内有效，也参与消息签名，从而限制旧交易重放。交易未在窗口内落链会过期，需要获取新 Blockhash、重建消息并重新签名。重签前必须查询旧签名的状态，因为 RPC 超时不代表旧交易没有落链；如果旧交易仍可能有效，直接重建可能造成重复支付。需要更长有效期的特定场景可以评估 Durable Nonce，但它引入额外账户和并发管理成本。

### 11. TON 中消息发送成功为什么不等于业务成功？

**回答思路**：异步消息链 -> 多阶段执行 -> Bounce/部分执行 -> 业务终态。

**参考答案**：

TON 通过异步消息驱动合约。外部消息被钱包合约接受，只能说明该阶段执行成功；它产生的内部消息还可能在目标合约执行时失败、Bounce，或形成后续消息链。Jetton 转账尤其不能只看入口交易，需要追踪 Jetton Wallet 之间的消息、操作码、Master 归属、目标账户状态和转账通知。统一钱包状态机应区分已提交、入口成功、消息处理中、最终成功、Bounce 和人工确认，避免把某一阶段的成功错误映射为资金到账。

### 12. 如何设计多链适配层？

**回答思路**：统一稳定能力 -> 保留链特有模型 -> 配置与版本 -> 隔离故障。

**参考答案**：

我会统一地址校验、费用估算、交易构建、签名载荷生成、广播、状态查询和区块扫描等稳定能力，并让上层使用统一业务状态；但 UTXO、nonce、Instruction、Message、Token Account 等模型保留链特有类型和扩展点。适配器不能返回含义模糊的通用 Map。链参数、节点路由、资产合约和确认策略要版本化配置。每条链使用独立队列、线程池、限流和熔断，避免单链节点故障拖垮全局。新链接入必须经过测试网、交易向量、重组/超时演练、限额灰度、对账和可回滚验证。

### 13. MySQL、Redis、MQ 在钱包系统中如何分工？

**回答思路**：事实源 -> 性能工具 -> 异步传递 -> 一致性组合。

**参考答案**：

MySQL 保存业务单、状态机、账本、链资源占用和审计记录，是资金正确性的事实源，依靠事务和唯一约束兜底。Redis 适合缓存、限流、短期幂等标记和降低锁竞争，但不能作为余额或资源分配的唯一依据。MQ 用于模块解耦、异步推进和削峰，默认按至少一次投递设计，消费者必须幂等。数据库状态和消息发布之间用本地事务写 Outbox，再由投递器或 CDC 发布；消费端用业务唯一键和状态前置条件处理重复、乱序与重试。

### 14. 为什么钱包需要独立账本和对账？

**回答思路**：三类事实 -> 双重记账 -> 多层对账 -> 差异处理。

**参考答案**：

链上交易、钱包业务状态和用户资产负债是三类不同事实，不能用一张充值表替代账本。独立账本用不可变分录记录可用、冻结、在途等余额变化，双重记账保证每笔业务借贷平衡，并可从流水重建余额。对账至少比较节点交易与钱包记录、地址资产与钱包汇总、平台链上资产与用户负债。发现差异后先分类和冻结风险操作，再通过补偿分录修正，不能直接改历史流水；所有补账都要审批、证据和审计。

### 15. 如何设计安全的签名服务？

**回答思路**：隔离 -> 交易可解释 -> 策略 -> 密钥保护 -> 审计与止损。

**参考答案**：

签名服务应与业务和公网隔离，私钥保存在 HSM、受控 KMS 或 MPC 节点中，不以明文进入应用内存或日志。它不能只接收一个哈希就盲签，而要独立解析规范化交易，验证链、资产、目标地址、金额、手续费、nonce/UTXO、合约和审批结果。请求通过双向认证，绑定业务单、时间窗、随机挑战和策略版本，防止伪造与重放。服务实施单笔/周期限额、地址与合约白名单、双人审批、速率限制和紧急停止。审计记录请求摘要、决策和密钥版本，但不记录私钥、助记词或敏感分片。

### 16. HSM、KMS、MPC 和多签如何选择？

**回答思路**：保护对象 -> 单点风险 -> 链兼容 -> 运维成本。

**参考答案**：

HSM 在硬件边界内生成和使用密钥，适合高强度密钥保护与审计；云 KMS 集成和运维更方便，但算法、权限和供应商边界受平台限制。MPC 将签名能力分散到多个参与方，避免完整私钥在单点出现，但协议实现、节点安全和恢复流程仍可能失败，并非绝对安全。链上多签由链或合约验证多个签名，规则透明，但依赖具体链能力并增加费用和操作复杂度。实际系统通常组合使用：热钱包强调自动化和严格限额，温钱包增加审批，冷钱包强调离线、多方控制和定期恢复演练。

### 17. 热钱包密钥疑似泄露时怎么办？

**回答思路**：停止损失 -> 资产迁移 -> 证据与范围 -> 密钥轮换 -> 恢复。

**参考答案**：

第一步立即暂停相关链和资产的自动提币、撤销签名权限并隔离可疑主机，同时避免破坏日志和取证数据。随后按预案将剩余资产转移到预先准备且独立生成的安全地址；不同链要处理 nonce、UTXO、Token 授权和 Gas 等细节。并行核对链上异常交易、访问日志、审批记录和密钥使用审计，确定影响范围，通知安全、合规和管理负责人。完成新密钥生成、权限重建、地址/合约配置切换和全量对账后，以低限额分批恢复。最后完成根因分析、用户与监管处置、凭据轮换和演练改进。

### 18. 节点或第三方 RPC 全部故障时如何降级？

**回答思路**：读写区分 -> 保守暂停 -> 保持内部可追踪 -> 恢复验证。

**参考答案**：

先用健康检查、区块高度、区块哈希和多供应商结果判断故障范围，避免把链停止出块误判为单节点故障。读服务可切换自建节点、备用供应商或缓存数据，但必须标注数据新鲜度；无法可靠确认链状态时暂停充值入账和新提币广播，已冻结的请求保持在可恢复状态，不能当作失败解冻。系统继续保存业务请求和 Outbox，防止丢单。恢复后先校验共同检查点、补扫缺失区块、核对未知广播交易和链资源状态，完成对账后再限流恢复服务。

### 19. 风控或 AML 服务不可用时应该放行提币吗？

**回答思路**：风险优先级 -> 分级降级 -> 状态保留 -> 恢复补偿。

**参考答案**：

默认不应绕过关键风控直接放行，因为一次错误放行可能不可逆。请求应保持冻结或待审核状态，并明确告知业务当前延迟。可以按已审批的降级策略区分低风险内部调度、小额白名单用户和高风险外部提币，但策略必须预先定义、限额、限时、可审计，不能在事故中临时口头决定。服务恢复后重新执行规则和名单检查，并处理规则版本变化。充值通常可以先检测和记录，但在风险判断完成前限制资产使用。

### 20. 如何优化吞吐不足的扫链模块？

**回答思路**：先度量 -> 定位瓶颈 -> 保持顺序边界 -> 有界并发 -> 验证资金语义。

**参考答案**：

先看扫描高度差、RPC 延迟与错误率、区块交易量、解析耗时、数据库慢查询、连接池、线程池和消息积压，确定瓶颈而不是直接加线程。常见优化包括批量 RPC、区块拉取与交易解析流水线化、按可安全并行的范围分片、地址集合本地索引、数据库批量写入和减少无效日志。区块检查点和重组检测仍需保持确定顺序，写入仍由唯一约束保证幂等。RPC、解析和数据库使用隔离线程池及有界队列，避免下游变慢导致内存失控。优化前后以相同区块回放，验证结果集合、顺序语义和重组恢复完全一致。

## 四、综合系统设计参考提纲

### 题目：设计支持 BTC、ETH、Solana、TON 的交易所托管钱包

**1. 先确认假设**

- 支持原生币和主流 Token，提供充值、提币、归集与内部调度。
- 账本系统已有或纳入本次设计；明确日交易量、峰值 TPS、地址量和可用性目标。
- 资金正确性和安全优先于实时性；允许链故障时暂停部分功能。

**2. 核心架构**

```text
用户/API
   |
账户账本 <-> 充值服务 <-> 扫链服务 <-> 链适配层 <-> 节点网关
   |              |                         |
风控合规 <-> 提币编排 -> 交易构建 -> 审批 -> 签名服务 -> 广播服务
   |                                              |
对账审计 <-> 归集与冷热调度 <------------------ 链上网络
```

**3. 数据与一致性**

- 业务表保存链、资产、业务单、交易哈希、状态、版本和审计时间。
- 账本使用不可变双重分录；金额统一使用最小单位整数。
- 充值按链上事件唯一键幂等，提币按业务单与链资源唯一约束幂等。
- 本地事务同时更新状态与 Outbox；MQ 消费者按至少一次投递处理。
- 所有外部超时先进入“结果未知”，查询实际状态后再决定重试。

**4. 四链特有处理**

| 链 | 资源/并发点 | Token 识别 | 失败恢复重点 |
|---|---|---|---|
| BTC | UTXO 预占 | 不适用或协议专项处理 | 双花、RBF/CPFP、重组 |
| EVM | 地址 nonce | 合约白名单 + Log | nonce gap、替换、Revert |
| Solana | Blockhash、账户锁 | Mint + Token Account/ATA | 过期、Commitment、重签核验 |
| TON | 钱包 `seqno`、消息链 | Jetton Master/Wallet | Bounce、异步终态、Memo |

**5. 安全设计**

- 地址服务只持有必要的公钥派生能力，不持有可直接消费资产的私钥。
- 热、温、冷钱包分层，热钱包设置单笔、日累计和余额上限。
- 签名服务独立部署，密钥由 HSM/KMS/MPC 保护，并独立解析交易和执行策略。
- 风控、合规、审批、签名职责分离；提供全局和单链紧急暂停开关。

**6. 高可用与可观测性**

- 自建节点与多供应商组合，读写节点池隔离，结果交叉验证。
- 单链独立队列、线程池、限流和熔断，避免故障扩散。
- 监控扫描高度差、充值延迟、提币各状态停留时间、广播/确认率、热钱包水位和对账差异。
- 为节点故障、链重组、签名故障、密钥泄露和账务差异准备 Runbook 并定期演练。

**7. 收尾时主动说明取舍**

> 这个设计用状态机、数据库约束和对账保证正确性，用 MQ 和异步流程提升吞吐；链故障时选择暂停而不是牺牲资金安全。下一步我会根据实际峰值、确认时效和密钥托管要求细化容量、表结构、部署拓扑与灾备等级。
