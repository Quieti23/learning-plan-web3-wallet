## 二、通用回答思路

### 1. 技术原理题：五段式

推荐结构：

> 结论 -> 核心原理 -> 钱包场景 -> 风险边界 -> 一句话总结

示例题：“Redis 分布式锁能否保证提币不重复？”

1. **结论**：不能单独保证，只能作为并发优化手段。
2. **原理**：锁可能因超时、主从切换、网络分区或进程停顿而失效。
3. **生产实现**：数据库业务单唯一键、状态迁移条件、链资源唯一约束承担最终正确性，Redis 只减少竞争。
4. **风险边界**：签名后崩溃、广播结果未知时不能直接创建新交易，必须先查询原交易。
5. **总结**：缓存和锁提高效率，数据库约束与链上核验守住资金正确性。

### 2. 流程设计题：状态机六问

回答充值、提币、归集等流程时，依次说明：

1. 输入从哪里来，信任边界在哪里？
2. 正常状态如何流转？
3. 业务唯一键和链上唯一标识是什么？
4. 每次状态迁移的前置条件是什么？
5. 超时、重复、乱序、重启、重组如何恢复？
6. 如何监控、对账、审计和人工兜底？

### 3. 系统设计题：八步法

1. **澄清需求**：支持哪些链和资产，充值/提币量级，安全等级，确认时效，合规要求。
2. **定义目标**：资金正确性优先，其次是安全、可恢复性、可用性和效率。
3. **划分模块**：节点网关、链适配、地址、扫描、充值、提币、归集、签名、账本、对账、风控。
4. **讲主流程**：先讲充值和提币两条主链路，不从技术组件堆砌开始。
5. **讲数据**：核心表、唯一键、状态机、金额类型和审计字段。
6. **讲一致性**：本地事务、Outbox、消费幂等、链资源锁和补偿。
7. **讲安全与容灾**：冷热分层、签名隔离、限额、多节点、暂停开关和恢复流程。
8. **讲观测与验证**：高度差、处理延迟、广播/确认率、余额水位、对账差异和故障演练。

### 4. 故障题：时间线法

> 先止损 -> 确认影响 -> 保全证据 -> 恢复一致性 -> 分批恢复 -> 复盘改进

不要一上来就“重启”或“重试”。资金系统先判断操作是否已经产生链上效果，再决定补偿动作。

### 5. 项目经历题：STAR + 复盘

- **S（背景）**：业务规模、原有问题、约束条件。
- **T（任务）**：你的职责和可衡量目标。
- **A（行动）**：你亲自完成的设计、实现、协作和取舍。
- **R（结果）**：延迟、吞吐、故障率、恢复时间或资金差异等数据。
- **复盘**：方案局限、后续改进，以及当时为什么没有选择另一方案。

当缺少直接钱包经验时，可以这样表达：

> 我没有把个人实践包装成生产经验。我的可迁移能力来自 Java 分布式系统中的幂等、一致性、状态机、审计和故障恢复；同时我已针对 BTC、EVM、Solana、TON 分别完成交易解析和钱包流程设计。我会明确哪些结论经过实践验证，哪些仍需要在真实业务量和安全流程下验证。

## 三、高频问题与参考答案

### 1. 交易所托管钱包和 MetaMask 有什么本质区别？

**回答思路**：密钥归属 -> 余额来源 -> 服务对象 -> 风险责任。

**参考答案**：

本质区别是资产控制权和账务模型。MetaMask 属于自托管钱包，私钥由用户持有，余额主要来自链上地址状态；交易所托管钱包由平台控制密钥，面向大量用户统一管理资金。用户看到的余额来自交易所内部账本，并不等于某个充值地址的链上余额。托管系统还必须处理地址分配、扫链、充值确认、提币审批、归集、冷热调度、签名隔离、对账和合规，因此其核心挑战不仅是“发一笔链上交易”，而是安全地维护链上资产与内部负债的一致性。

### 2. 如何保证充值不重不漏？

**回答思路**：扫描游标 -> 业务唯一键 -> 状态机 -> 重组 -> 重扫与对账。

**参考答案**：

我会采用“至少一次扫描 + 幂等入账”，而不是依赖扫描只执行一次。扫描器按区块高度推进，同时保存区块哈希，用父块关系检测重组。充值记录使用链上稳定标识建立唯一约束，例如 BTC 使用 `txid + vout`，EVM Token 使用 `chainId + txHash + logIndex`。发现充值后先进入待确认状态，达到按链、资产、金额和风险配置的确认条件后，在同一数据库事务中写入账本分录、更新充值状态并写 Outbox。重复消息由唯一索引和状态迁移条件拦截。系统还要支持历史重扫、扫描高度差监控、链上与内部账本对账；发生重组时将受影响记录回退，必要时冻结相关余额并进入人工处理。

### 3. 已经入账的充值发生链重组怎么办？

**回答思路**：检测 -> 标记影响 -> 逆向账务 -> 风险控制 -> 重新确认。

**参考答案**：

扫描器通过已保存区块哈希与当前规范链比较发现重组，找到共同祖先后回退受影响区块。尚未入账的充值退回待确认或作废；已入账的充值不能直接删除流水，而应写冲正分录并保留完整审计记录。如果用户已使用这笔余额，应冻结账户可用余额、阻断相关提币，并按负余额或人工审核流程处理。若交易重新出现在规范链上，则按新的区块位置重新累计确认。大额充值采用更高确认数，是降低这种损失概率的手段，但不能替代重组处理机制。

### 4. 如何保证提币不重复？

**回答思路**：请求层 -> 账本层 -> 链资源层 -> 签名层 -> 广播未知结果。

**参考答案**：

提币需要多层幂等。请求层使用用户请求号或平台业务单号唯一约束；账本层在事务中冻结余额，确保同一业务单只冻结一次；构建层锁定链特有资源，例如 BTC 的 UTXO、EVM 的 nonce、TON 的 `seqno`。签名请求绑定业务单、交易摘要和策略版本，签名服务拒绝重复或不符合审批结果的请求。广播可以重复发送同一份已签名原始交易，因为其交易哈希不变，但广播超时后绝不能直接构建新交易，必须先按原交易哈希、nonce、UTXO 等查询链上和节点状态。最终通过状态机条件更新、唯一约束和链上对账收敛。

### 5. 提币余额应该何时扣减？

**回答思路**：可用余额与所有权语义 -> 冻结 -> 最终扣减/解冻。

**参考答案**：

用户提交并通过基础校验后，应先将金额和预计手续费从可用余额转为冻结余额，防止重复消费；不能等到链上确认才控制余额。提币进入不可逆阶段后，根据账务规则把冻结余额正式扣减；若在签名前被拒绝或安全取消，则解冻。广播后结果未知不能轻易解冻，因为交易可能已经进入网络。具体“正式扣减”发生在广播还是确认可以由业务会计政策决定，但状态必须能表达在途资金，并保证账本分录不可变、可审计、可补偿。

### 6. 广播请求超时后怎么处理？

**回答思路**：未知不等于失败 -> 保留原交易 -> 多维查询 -> 同原文重播或链特定替换。

**参考答案**：

超时只表示客户端不知道结果，不表示节点没有接收。系统应把任务标记为“广播结果未知”，保留完整已签名交易和预期哈希，先向多个节点查询交易、Mempool 和链上资源状态。查到原交易就继续跟踪；暂时查不到时，可以幂等地重播同一原始交易。只有确认原交易未生效且满足链特定条件，才允许重建或替换，例如 EVM 使用相同 nonce 和更高费用替换，BTC 使用 RBF 或 CPFP。任何新建动作都需要审计和防双付检查。

### 7. BTC UTXO 与 EVM nonce 的并发控制有什么不同？

**回答思路**：冲突资源 -> 锁定方式 -> 失败影响 -> 恢复。

**参考答案**：

BTC 的冲突资源是离散 UTXO。同一个 UTXO 只能被一笔确认交易消费，因此构建时要在数据库中原子预占，并在失败或过期后按状态释放；不同 UTXO 可以并行。EVM 同一发送地址的交易按 nonce 排序，分配重复 nonce 会产生替换竞争，出现 nonce gap 又会阻塞后续交易，因此通常由持久化 nonce 管理器串行分配，数据库锁和唯一约束负责正确性。恢复时 BTC 核对 UTXO 是否已花费，EVM 则同时比较 confirmed nonce、pending 交易和本地分配记录。

### 8. EIP-1559 手续费如何计算？

**回答思路**：上限字段 -> 实际单价 -> 总费用 -> 退款语义。

**参考答案**：

用户设置 `maxFeePerGas` 和 `maxPriorityFeePerGas`。实际单价通常为：

$$
\text{effectiveGasPrice}=\min(\text{maxFeePerGas},\ \text{baseFee}+\text{maxPriorityFeePerGas})
$$

实际费用为：

$$
\text{fee}=\text{gasUsed}\times\text{effectiveGasPrice}
$$

`baseFee` 被销毁，小费给出块者。`gasLimit` 是最多允许消耗的 Gas，不是一定收取的数量；未使用部分不会按上限收费，但交易执行失败通常仍要支付已经消耗的 Gas。

### 9. ERC-20 充值为什么不能只看交易的 `to` 和 `value`？

**回答思路**：外层交易 -> 合约执行 -> Event Log -> 非标准代币。

**参考答案**：

ERC-20 转账时，外层交易的 `to` 通常是 Token 合约地址，`value` 通常为零，真正的收款地址和数量位于调用数据及执行结果中。充值识别应校验链、官方 Token 合约地址、成功 Receipt，并解析标准 `Transfer` Event 的 `from`、`to` 和 `value`，唯一键通常包含 `txHash + logIndex`。还要考虑代理合约、内部调用、手续费代币、Rebase 及非标准事件，所以资产接入前必须建立白名单和专项解析测试，不能仅凭代币名称或符号识别。

### 10. Solana 的 Recent Blockhash 有什么作用？

**回答思路**：新鲜度与防重放 -> 有效窗口 -> 过期恢复 -> 重复支付风险。

**参考答案**：

Recent Blockhash 让交易只在有限窗口内有效，也参与消息签名，从而限制旧交易重放。交易未在窗口内落链会过期，需要获取新 Blockhash、重建消息并重新签名。重签前必须查询旧签名的状态，因为 RPC 超时不代表旧交易没有落链；如果旧交易仍可能有效，直接重建可能造成重复支付。需要更长有效期的特定场景可以评估 Durable Nonce，但它引入额外账户和并发管理成本。

### 11. TON 中消息发送成功为什么不等于业务成功？

**回答思路**：异步消息链 -> 多阶段执行 -> Bounce/部分执行 -> 业务终态。

**参考答案**：

TON 通过异步消息驱动合约。外部消息被钱包合约接受，只能说明该阶段执行成功；它产生的内部消息还可能在目标合约执行时失败、Bounce，或形成后续消息链。Jetton 转账尤其不能只看入口交易，需要追踪 Jetton Wallet 之间的消息、操作码、Master 归属、目标账户状态和转账通知。统一钱包状态机应区分已提交、入口成功、消息处理中、最终成功、Bounce 和人工确认，避免把某一阶段的成功错误映射为资金到账。

### 12. 如何设计多链适配层？

**回答思路**：统一稳定能力 -> 保留链特有模型 -> 配置与版本 -> 隔离故障。

**参考答案**：

我会统一地址校验、费用估算、交易构建、签名载荷生成、广播、状态查询和区块扫描等稳定能力，并让上层使用统一业务状态；但 UTXO、nonce、Instruction、Message、Token Account 等模型保留链特有类型和扩展点。适配器不能返回含义模糊的通用 Map。链参数、节点路由、资产合约和确认策略要版本化配置。每条链使用独立队列、线程池、限流和熔断，避免单链节点故障拖垮全局。新链接入必须经过测试网、交易向量、重组/超时演练、限额灰度、对账和可回滚验证。

### 13. MySQL、Redis、MQ 在钱包系统中如何分工？

**回答思路**：事实源 -> 性能工具 -> 异步传递 -> 一致性组合。

**参考答案**：

MySQL 保存业务单、状态机、账本、链资源占用和审计记录，是资金正确性的事实源，依靠事务和唯一约束兜底。Redis 适合缓存、限流、短期幂等标记和降低锁竞争，但不能作为余额或资源分配的唯一依据。MQ 用于模块解耦、异步推进和削峰，默认按至少一次投递设计，消费者必须幂等。数据库状态和消息发布之间用本地事务写 Outbox，再由投递器或 CDC 发布；消费端用业务唯一键和状态前置条件处理重复、乱序与重试。

### 14. 为什么钱包需要独立账本和对账？

**回答思路**：三类事实 -> 双重记账 -> 多层对账 -> 差异处理。

**参考答案**：

链上交易、钱包业务状态和用户资产负债是三类不同事实，不能用一张充值表替代账本。独立账本用不可变分录记录可用、冻结、在途等余额变化，双重记账保证每笔业务借贷平衡，并可从流水重建余额。对账至少比较节点交易与钱包记录、地址资产与钱包汇总、平台链上资产与用户负债。发现差异后先分类和冻结风险操作，再通过补偿分录修正，不能直接改历史流水；所有补账都要审批、证据和审计。

### 15. 如何设计安全的签名服务？

**回答思路**：隔离 -> 交易可解释 -> 策略 -> 密钥保护 -> 审计与止损。

**参考答案**：

签名服务应与业务和公网隔离，私钥保存在 HSM、受控 KMS 或 MPC 节点中，不以明文进入应用内存或日志。它不能只接收一个哈希就盲签，而要独立解析规范化交易，验证链、资产、目标地址、金额、手续费、nonce/UTXO、合约和审批结果。请求通过双向认证，绑定业务单、时间窗、随机挑战和策略版本，防止伪造与重放。服务实施单笔/周期限额、地址与合约白名单、双人审批、速率限制和紧急停止。审计记录请求摘要、决策和密钥版本，但不记录私钥、助记词或敏感分片。

### 16. HSM、KMS、MPC 和多签如何选择？

**回答思路**：保护对象 -> 单点风险 -> 链兼容 -> 运维成本。

**参考答案**：

HSM 在硬件边界内生成和使用密钥，适合高强度密钥保护与审计；云 KMS 集成和运维更方便，但算法、权限和供应商边界受平台限制。MPC 将签名能力分散到多个参与方，避免完整私钥在单点出现，但协议实现、节点安全和恢复流程仍可能失败，并非绝对安全。链上多签由链或合约验证多个签名，规则透明，但依赖具体链能力并增加费用和操作复杂度。实际系统通常组合使用：热钱包强调自动化和严格限额，温钱包增加审批，冷钱包强调离线、多方控制和定期恢复演练。

### 17. 热钱包密钥疑似泄露时怎么办？

**回答思路**：停止损失 -> 资产迁移 -> 证据与范围 -> 密钥轮换 -> 恢复。

**参考答案**：

第一步立即暂停相关链和资产的自动提币、撤销签名权限并隔离可疑主机，同时避免破坏日志和取证数据。随后按预案将剩余资产转移到预先准备且独立生成的安全地址；不同链要处理 nonce、UTXO、Token 授权和 Gas 等细节。并行核对链上异常交易、访问日志、审批记录和密钥使用审计，确定影响范围，通知安全、合规和管理负责人。完成新密钥生成、权限重建、地址/合约配置切换和全量对账后，以低限额分批恢复。最后完成根因分析、用户与监管处置、凭据轮换和演练改进。

### 18. 节点或第三方 RPC 全部故障时如何降级？

**回答思路**：读写区分 -> 保守暂停 -> 保持内部可追踪 -> 恢复验证。

**参考答案**：

先用健康检查、区块高度、区块哈希和多供应商结果判断故障范围，避免把链停止出块误判为单节点故障。读服务可切换自建节点、备用供应商或缓存数据，但必须标注数据新鲜度；无法可靠确认链状态时暂停充值入账和新提币广播，已冻结的请求保持在可恢复状态，不能当作失败解冻。系统继续保存业务请求和 Outbox，防止丢单。恢复后先校验共同检查点、补扫缺失区块、核对未知广播交易和链资源状态，完成对账后再限流恢复服务。

### 19. 风控或 AML 服务不可用时应该放行提币吗？

**回答思路**：风险优先级 -> 分级降级 -> 状态保留 -> 恢复补偿。

**参考答案**：

默认不应绕过关键风控直接放行，因为一次错误放行可能不可逆。请求应保持冻结或待审核状态，并明确告知业务当前延迟。可以按已审批的降级策略区分低风险内部调度、小额白名单用户和高风险外部提币，但策略必须预先定义、限额、限时、可审计，不能在事故中临时口头决定。服务恢复后重新执行规则和名单检查，并处理规则版本变化。充值通常可以先检测和记录，但在风险判断完成前限制资产使用。

### 20. 如何优化吞吐不足的扫链模块？

**回答思路**：先度量 -> 定位瓶颈 -> 保持顺序边界 -> 有界并发 -> 验证资金语义。

**参考答案**：

先看扫描高度差、RPC 延迟与错误率、区块交易量、解析耗时、数据库慢查询、连接池、线程池和消息积压，确定瓶颈而不是直接加线程。常见优化包括批量 RPC、区块拉取与交易解析流水线化、按可安全并行的范围分片、地址集合本地索引、数据库批量写入和减少无效日志。区块检查点和重组检测仍需保持确定顺序，写入仍由唯一约束保证幂等。RPC、解析和数据库使用隔离线程池及有界队列，避免下游变慢导致内存失控。优化前后以相同区块回放，验证结果集合、顺序语义和重组恢复完全一致。

## 四、综合系统设计参考提纲

### 题目：设计支持 BTC、ETH、Solana、TON 的交易所托管钱包

**1. 先确认假设**

- 支持原生币和主流 Token，提供充值、提币、归集与内部调度。
- 账本系统已有或纳入本次设计；明确日交易量、峰值 TPS、地址量和可用性目标。
- 资金正确性和安全优先于实时性；允许链故障时暂停部分功能。

**2. 核心架构**

```text
用户/API
   |
账户账本 <-> 充值服务 <-> 扫链服务 <-> 链适配层 <-> 节点网关
   |              |                         |
风控合规 <-> 提币编排 -> 交易构建 -> 审批 -> 签名服务 -> 广播服务
   |                                              |
对账审计 <-> 归集与冷热调度 <------------------ 链上网络
```

**3. 数据与一致性**

- 业务表保存链、资产、业务单、交易哈希、状态、版本和审计时间。
- 账本使用不可变双重分录；金额统一使用最小单位整数。
- 充值按链上事件唯一键幂等，提币按业务单与链资源唯一约束幂等。
- 本地事务同时更新状态与 Outbox；MQ 消费者按至少一次投递处理。
- 所有外部超时先进入“结果未知”，查询实际状态后再决定重试。

**4. 四链特有处理**

| 链 | 资源/并发点 | Token 识别 | 失败恢复重点 |
|---|---|---|---|
| BTC | UTXO 预占 | 不适用或协议专项处理 | 双花、RBF/CPFP、重组 |
| EVM | 地址 nonce | 合约白名单 + Log | nonce gap、替换、Revert |
| Solana | Blockhash、账户锁 | Mint + Token Account/ATA | 过期、Commitment、重签核验 |
| TON | 钱包 `seqno`、消息链 | Jetton Master/Wallet | Bounce、异步终态、Memo |

**5. 安全设计**

- 地址服务只持有必要的公钥派生能力，不持有可直接消费资产的私钥。
- 热、温、冷钱包分层，热钱包设置单笔、日累计和余额上限。
- 签名服务独立部署，密钥由 HSM/KMS/MPC 保护，并独立解析交易和执行策略。
- 风控、合规、审批、签名职责分离；提供全局和单链紧急暂停开关。

**6. 高可用与可观测性**

- 自建节点与多供应商组合，读写节点池隔离，结果交叉验证。
- 单链独立队列、线程池、限流和熔断，避免故障扩散。
- 监控扫描高度差、充值延迟、提币各状态停留时间、广播/确认率、热钱包水位和对账差异。
- 为节点故障、链重组、签名故障、密钥泄露和账务差异准备 Runbook 并定期演练。

**7. 收尾时主动说明取舍**

> 这个设计用状态机、数据库约束和对账保证正确性，用 MQ 和异步流程提升吞吐；链故障时选择暂停而不是牺牲资金安全。下一步我会根据实际峰值、确认时效和密钥托管要求细化容量、表结构、部署拓扑与灾备等级。
