## 第一轮面试：部门主管

**参考回答：**
我主要做过 Web3 相关的开发和业务支持工作，重点关注钱包、链上数据、充值提币、账本、风控和交易执行等方向。整体上，我比较熟悉区块链基础结构、链上数据解析、账户与交易模型、数据库设计，以及常见工程化问题。

在项目中，我会比较关注资金安全、数据一致性、异常恢复和可观测性，而不是只看功能能不能跑通。目前我希望继续在 Web3 方向深耕，尤其是钱包、链上基础设施、交易系统和安全相关方向。

### 2. 详细介绍之前的 Web3 项目

**参考回答框架：**
1. 项目背景：项目做什么，服务什么用户，解决什么问题。
2. 我的职责：我负责哪一块，和哪些角色协作。
3. 系统架构：链上、后端、数据库、索引、钱包/签名/风控等模块如何分工。
4. 关键流程：充值、提币、地址生成、链上监听、对账、异常处理。
5. 难点与方案：一致性、幂等、重试、重组、手续费、性能、安全。
6. 结果：性能提升、稳定性提升、错误率下降、业务效率提升等。

### 3. 以太坊中有哪些树

**标准答案：**
以太坊里常见的三类树是：交易树（Transaction Trie）、收据树（Receipt Trie）和状态树（State Trie）。它们底层都使用 Merkle Patricia Trie（MPT）。

### 4. 为什么需要收据树

**标准答案：**
收据树用于把交易执行后的结果结构化存储起来，方便查询、索引和证明。交易只表示“发起了什么操作”，收据记录“执行结果是什么”，例如是否成功、gas used、logs/events、状态变化摘要等。收据树也方便轻客户端验证和区块浏览器检索。

### 5. 以太坊里的状态是什么，状态树怎么存状态

**标准答案：**
以太坊全局状态是所有账户状态的集合。每个账户通常包含 `balance`、`nonce`、`codeHash`、`storageRoot`。这些账户状态存放在状态树（State Trie）中，底层使用 MPT。

### 6. 合约数据的储存形式

**标准答案：**
合约数据可以理解为两层：账户层和存储层。合约账户本身在全局状态树中，账户里有 `storageRoot`；`storageRoot` 指向该合约自己的 storage trie。也就是说，合约状态也是通过 MPT 组织的，只不过是“全局状态树 + 合约存储树”的嵌套结构。

### 7. 比特币里的交易是怎么存的

**标准答案：**
比特币区块中的交易通常用 Merkle Tree 组织，叶子节点是交易哈希，逐层哈希汇总到 Merkle Root，Merkle Root 写入区块头。

### 8. Merkle Tree 的性质、优点，为什么用它存

**标准答案：**
Merkle Tree 的优点包括：完整性验证、高效证明、适合 SPV、篡改检测。它能在保证完整性的同时，把验证成本降到很低。

### 9. 为什么以太坊要将 MT 改成 MPT

**标准答案：**
以太坊选择 MPT 是因为它不仅要证明数据存在，还要支持键值映射和状态查询。普通 Merkle Tree 更适合固定顺序的叶子集合，而 MPT 更适合表示“账户地址/存储槽 -> 值”的键值结构，并且支持前缀压缩，适合稀疏状态存储。

### 10. 比特币里的 UTXO

**标准答案：**
UTXO 是 Unspent Transaction Output，即未花费交易输出。比特币余额不是直接记在账户上，而是由一组 UTXO 汇总而成。每笔交易消耗旧的 UTXO，生成新的 UTXO。

### 11. 比特币查询余额只能从头开始遍历整条链吗

**标准答案：**
不是。常见高效方法包括维护 UTXO Set、通过索引或钱包数据库记录地址相关 UTXO、在区块扫描时增量更新状态。实际查询余额通常不靠全链遍历，而是靠本地或服务端维护的 UTXO 索引。

### 12. 比特币地址是怎么生成的

**标准答案：**
路径可以理解为：助记词 -> seed -> 私钥 -> 公钥 -> PubKeyHash -> address。其中前半部分是单向派生，PubKeyHash 转 address 时会经过编码和版本信息处理，常见有 Base58Check 编码。

### 13. 关于数据库索引：hash 索引与 B+ 树索引的适用场景，为什么用 B+ 树索引

**标准答案：**
Hash 索引适合等值查询，速度快，但不适合范围查询、排序和前缀匹配。B+ 树索引适合范围查询、排序、最左前缀匹配，也更适合数据库的通用查询模式，因此更常用。

### 14. 主键与非主键和索引的关系

**标准答案：**
在 InnoDB 中，主键通常是聚簇索引；非主键索引通常是二级索引。通过二级索引查数据时，可能需要回表到主键索引查询完整行数据。

### 15. 进程、线程、协程的区别

**标准答案：**
进程是资源分配的基本单位，线程是 CPU 调度的基本单位，协程是用户态轻量并发单位，由程序或运行时调度，切换成本更低。

### 16. Golang 协程间如何通信

**标准答案：**
Go 协程之间通常通过 channel 通信，也可以通过共享内存 + 锁，但更推荐用“通过通信来共享内存”的方式。

### 17. 算法问题：判断链表是否有环

**标准答案：**
使用快慢指针：慢指针每次走一步，快指针每次走两步。如果有环，两个指针一定会相遇；如果快指针先到 nil，说明无环。

### 18. 堆排序、快速排序的时间复杂度以及适用场景

**标准答案：**
堆排序平均和最坏都是 `O(n log n)`，适合对最坏情况有要求的场景。快速排序平均是 `O(n log n)`，最坏是 `O(n^2)`，但通常常数较小、实践中很快。

### 3. 聊上一家 Web3 项目

**参考回答框架：**
项目背景、业务目标、技术架构、个人职责、难点和解决方案、结果和反思。

### 4. 为什么用区块链？区块链的创新点在哪

**标准答案：**
区块链的创新点主要是：去中心化信任、不可篡改和可追溯、共识机制、可编程资产、开放验证。当业务需要跨主体协作、去信任化对账、公开可验证资产流转时，区块链更有价值。

### 5. Web3 项目开发的技术难点

**标准答案：**
常见难点包括链上链下数据一致性、交易状态的不确定性、充值/提币幂等处理、链重组和确认数问题、签名和密钥安全、多链协议差异、风控合规和审计要求、节点稳定性和第三方依赖。

### 6. 以太坊相比于比特币的创新点

**标准答案：**
以太坊的主要创新点包括智能合约、账户模型、复杂状态存储和执行逻辑、丰富的应用生态，以及通过 EVM 提供更强的可编程性。

### 7. 区块链落地场景

**标准答案：**
数字资产支付和转账、跨境结算、钱包与托管、DeFi、NFT/数字藏品、供应链溯源、身份与凭证、RWA/资产上链等。

### 8. 为什么会选择 Web3 行业

**参考回答：**
我会从技术挑战、行业价值和个人匹配三个角度回答：Web3 涉及链上协议、资金安全、分布式系统和安全工程，复杂度高；它把资产、信任和协作机制重新组织；而我的经验和兴趣也更适合做偏底层、偏安全、偏工程化的工作。

### 9. 理解的行业风险

**标准答案：**
行业风险主要包括政策与合规风险、市场波动和资产价格风险、智能合约漏洞风险、私钥泄露和资金安全风险、节点/RPC/桥和第三方依赖风险、业务欺诈和风控风险、项目方治理和运营风险。

### 10. 之前工资

**回答建议：**
尽量基于真实情况回答。可以直接说明税前/税后、年包结构和固定/浮动部分；如果不想展开，可以礼貌地说“我更希望先聊岗位匹配和职责范围，薪资可以后面结合整体 package 再对齐”。

### 11. 聊 Web3 行业

**建议方向：**
行业发展阶段、基础设施成熟度、钱包/交易/合规/RWA/支付方向、多链与跨链复杂性、未来机会与个人成长路径。
