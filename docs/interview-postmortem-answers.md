### 2. 详细介绍之前的 Web3 项目

**完整回答：**

我先说明项目性质：当前我能完整展开的是一个支持 BTC、EVM、Solana、TON 的托管钱包个人研究与架构设计，不是生产上线项目。它的目标是把多条链接入统一的钱包业务体系，覆盖地址管理、充值扫描、提币、归集、账本、风控、签名、节点网关和对账。

架构上我把系统分成三类事实。第一类是链上事实，包括区块、交易、Receipt、Event、Instruction、Message、确认和重组证据；第二类是业务状态，例如充值待确认、提币已冻结、待签名、广播结果未知；第三类是内部账本，记录可用、冻结、在途余额和不可变分录。三者分开保存，用稳定业务 ID 关联，因为“链上查到交易”“业务允许处理”和“用户余额已经变化”不是同一件事。

以提币为例，请求进入后先通过 `clientRequestId` 做幂等校验，在数据库事务中创建业务单并冻结余额，再经过风控与审批。之后由链适配器分配链特有资源：BTC 预占 UTXO，EVM 分配 nonce，Solana 固化 Blockhash 相关上下文，TON 分配 `seqno`。交易构建完成后，独立签名服务从待签名字节重新解析地址、金额、资产、手续费和链资源，确认与审批意图一致后才调用 HSM、KMS 或 MPC。签名原文和预期交易哈希先落库再广播；如果广播超时，状态进入 `BROADCAST_UNKNOWN`，先查原交易，不能直接新建第二笔交易。

一致性方面，我使用“短本地事务 + 状态机 + Outbox + 至少一次消息 + 幂等消费”。MySQL 是资金事实源，Redis 只做缓存、限流和降低竞争，MQ 负责异步传播但不承诺端到端恰好一次。充值使用链上稳定位置做唯一键，例如 BTC 是 `txid + vout`，ERC-20 是 `chainId + txHash + logIndex`；账本再按业务命令唯一，确保重复扫描和消息重投只产生一次资金效果。

这个方案最难的地方不是画出正常流程，而是处理未知结果和链差异。我的取舍是资金正确性优先于可用性：节点、风控或签名证据不足时暂停推进；重组或纠错使用冲正分录，不删除历史；恢复完成的标准是链事实、业务状态、账本、签名记录和链上交易完成对账。

这个项目目前的成果是形成了完整架构图、四链差异表、状态机、核心表与唯一键设计、异常恢复矩阵和面试答辩材料。它证明了我的方案设计和学习能力，但不能证明生产容量、真实资金安全或合规流程已经验证；这些需要进入真实环境后通过安全评审、测试网、故障注入和小额灰度补齐。

### 3. 以太坊中有哪些树

**完整回答：**

如果讨论执行层区块头中直接承诺的数据，核心有三棵 Trie：状态树、交易树和收据树，区块头分别保存 `stateRoot`、`transactionsRoot` 和 `receiptsRoot`。它们都采用 Merkle Patricia Trie，节点经过编码和哈希。

- **状态树**保存全局账户状态，值包括账户的 nonce、balance、storageRoot 和 codeHash。
- **交易树**保存区块内按交易索引组织的交易数据，证明某笔交易被该区块包含。
- **收据树**保存交易执行后的 Receipt，包括执行状态、累计 Gas、日志 Bloom 和 Logs。

此外，合约账户的 `storageRoot` 又指向该合约自己的存储 Trie，所以状态树下面还嵌套了大量合约存储树。面试中我会先回答三棵区块级核心 Trie，再补充合约 storage trie。

### 4. 为什么需要收据树

**完整回答：**

交易只描述用户希望执行什么，不能证明实际执行结果。收据树把每笔交易执行后的结果纳入区块头承诺，使节点和轻客户端能够验证某个 Receipt 属于该区块，而不必信任区块浏览器或第三方索引器。

Receipt 中关键内容包括交易成功或失败状态、累计 Gas、Logs Bloom 和事件日志。钱包处理 ERC-20 充值时，不能只看外层交易的 `to` 和 `value`，而要确认 Receipt 成功，并解析官方 Token 合约发出的 `Transfer` Log；`txHash + logIndex` 还能区分同一交易中的多次转账。

需要纠正一个常见说法：Receipt 不直接保存完整的“状态变化摘要”，也不保存所有内部调用。状态变化最终由新的 `stateRoot` 承诺，内部调用分析通常依赖 Trace API，而 Trace 不是共识层 Receipt 的组成部分。

### 5. 以太坊里的状态是什么，状态树怎么存状态

**完整回答：**

以太坊状态是某一确定区块执行完成后，全网账户和合约存储的快照。它不是区块里所有交易的简单集合，而是从创世状态开始，按规范顺序执行交易后得到的状态转换结果。

全局状态树通过账户地址对应的键定位账户。EOA 和合约账户都包含 `nonce`、`balance`、`storageRoot`、`codeHash`。合约账户通过 `codeHash` 关联代码，通过 `storageRoot` 指向自己的存储 Trie。合约状态变量最终被编译器映射到 32 字节 slot，mapping 和动态数组的位置通常由键和槽位号哈希计算。

任意账户或存储槽改变都会沿路径改变哈希并最终改变 `stateRoot`。节点可用 Merkle Proof 验证账户或槽位在某状态根下的值。钱包仍不能把一次 RPC 余额直接当作内部用户账本，因为链上账户事实与平台确认、冻结和在途状态不是同一层数据。

### 6. 合约数据的储存形式

**完整回答：**

合约数据主要分为代码、持久化存储、临时内存、调用数据和日志，不能全部笼统地说成 storage。

- 合约字节码由账户的 `codeHash` 关联。
- 持久化状态位于合约自己的 storage trie，逻辑上是 `256-bit slot -> 256-bit value`。
- `memory` 只在一次调用期间存在，交易结束后消失。
- `calldata` 是只读调用输入，不属于持久化状态。
- Event Log 写入交易 Receipt，便于索引，但合约不能像读取 storage 一样读取历史日志。

Solidity 静态变量通常按布局打包到连续 slot；mapping 元素位置一般由 `keccak256(key, slot)` 推导；动态数组从哈希位置展开。代理合约升级时必须保持 storage layout 兼容，否则新实现可能用不同变量解释旧 slot，造成状态破坏。

### 7. 比特币里的交易是怎么存的

**完整回答：**

比特币交易完整序列化后存放在区块体中，区块内交易按顺序组成列表。区块头不保存全部交易，只保存由交易 ID 构建出的 Merkle Root。验证某笔交易是否属于区块时，只需交易哈希和 Merkle Path，验证成本为 `O(log n)`。

一笔交易由 inputs 和 outputs 组成。输入引用旧交易的 `txid + vout` 并提供解锁数据；输出包含金额和 `scriptPubKey`。除 coinbase 外，交易不是从账户扣余额，而是消费已有 UTXO 并创建新 UTXO。节点会增量维护 UTXO Set，但它是从区块派生的验证状态，不等同于区块中的原始交易存储。

SegWit 后还要区分 `txid` 和 `wtxid`。传统 Merkle Root 使用不含 Witness 的 `txid`，Witness 数据通过 coinbase 中的 witness commitment 另行承诺。

### 8. Merkle Tree 的性质、优点，为什么用它存

**完整回答：**

Merkle Tree 的叶子保存数据哈希，父节点保存子节点哈希，最终用一个根哈希承诺整组数据。任何叶子变化都会传导到根，因此具备强篡改检测能力。

它的主要优点是：成员证明只需长度约为 `log₂(n)` 的兄弟哈希路径；可以快速比较数据集合是否一致；区块头只需固定长度的根，就能承诺可变数量的交易。这适合比特币 SPV，轻客户端保存区块头，通过 Merkle Proof 验证交易被某个区块包含。

但 Merkle Proof 只证明交易被区块包含，不单独证明交易最终不可逆，也不证明其输出尚未花费，还要结合区块头链、工作量、确认深度和 UTXO 验证。比特币使用它，是因为区块内交易是相对稳定的有序集合，重点是高效承诺和包含性证明。

### 9. 为什么以太坊要将 MT 改成 MPT

**完整回答：**

更准确地说，不是简单把比特币的 Merkle Tree 改造，而是以太坊的状态需求不同，因此选择了结合 Merkle Tree 与 Patricia Trie 的键值认证结构。

普通二叉 Merkle Tree 适合对按位置排列的叶子做集合承诺，但以太坊需要频繁按地址和存储键查询、插入、更新，还要支持存在证明和不存在证明。Patricia Trie 按 key 的 nibble 路径查找，并通过 extension node 压缩公共前缀；再对节点哈希，就获得可验证性。根哈希既能承诺整个键值状态，也能提供与路径长度相关的证明。

MPT 也有节点多、随机读写和数据库放大严重、实现复杂等代价，这也是以太坊研究 Verkle Tree 等结构的原因。它不是无条件“更高级”，而是针对动态键值状态、证明和确定性根哈希的取舍。

### 10. 比特币里的 UTXO

**完整回答：**

UTXO 是尚未被后续交易消费的交易输出。每个 UTXO 由 `txid + vout` 唯一定位，包含金额和锁定脚本。用户所谓的 BTC 余额，本质上是其可控制脚本对应的一组 UTXO 金额之和。

发起交易时，钱包选择一个或多个 UTXO 作为输入。若输入总额大于收款金额加手续费，通常创建找零输出；手续费等于输入总额减输出总额。交易确认后，旧 UTXO 被消费，新 outputs 成为新的 UTXO。

对托管钱包而言，UTXO 也是并发资源。两个提币任务若选中同一个 UTXO，会产生双花冲突。构建前要在 MySQL 中原子预占 outpoint 并建立唯一约束；Redis 锁只能减少竞争。恢复时根据链上和 Mempool 证据判断是否已消费，不能因本地锁过期就释放。

### 11. 比特币查询余额只能从头开始遍历整条链吗

**完整回答：**

不需要每次都从创世区块遍历。全节点验证区块时会增量维护 UTXO Set：消费输入时删除旧 UTXO，产生输出时加入新 UTXO，因此可以查询当前未花费状态。

但 Bitcoin Core 默认不是按任意地址高效查询完整历史的浏览器数据库。钱包通常维护自己的 descriptor、地址和交易索引；交易所会在扫链过程中把受控地址相关输出增量写入数据库，记录创建、预占、消费和确认状态。也可使用 `scantxoutset` 或专门索引器，但第三方浏览器不能成为唯一资金事实源。

生产恢复时可能从可信 checkpoint 重扫区块或重建索引，但这不是每次查余额的正常路径。内部用户余额也不能直接等于链上 UTXO 总和，因为用户权益由平台账本维护，链上资金可能已归集并混合。

### 12. 比特币地址是怎么生成的

**完整回答：**

HD 钱包的一般流程是：安全熵生成助记词，BIP-39 通过 PBKDF2 得到 Seed，BIP-32 派生主扩展密钥，再按 BIP-44/49/84/86 等路径派生子私钥和公钥。之后的地址生成取决于脚本类型，不是统一的“公钥哈希后 Base58”。

- P2PKH：压缩公钥做 SHA-256 和 RIPEMD-160，加入网络版本后 Base58Check 编码。
- P2SH：对 redeem script 做 Hash160，再用 Base58Check 编码。
- P2WPKH/P2WSH：编码 witness version 和 program，通常使用 Bech32。
- P2TR：基于调整后的 x-only 公钥或脚本树承诺，使用 Bech32m。

地址包含网络和脚本类型信息，但不包含余额，也不是公钥本身。生产系统必须校验网络、校验和、脚本类型与支持策略。助记词和扩展私钥不能进入普通业务服务；地址服务宜只持有受控扩展公钥或预生成地址，并保存派生路径、版本和根公钥指纹用于灾备。

### 13. Hash 索引与 B+ 树索引的适用场景，为什么用 B+ 树索引

**完整回答：**

Hash 索引把键映射到桶，适合完整键等值查询，平均查找接近 `O(1)`；但通常不保留顺序，因此不适合范围查询、排序、`BETWEEN`、前缀扫描，也不能很好支持组合索引的最左前缀。

B+ 树是有序多路平衡树，非叶子节点保存导航键，叶子保存记录或主键并通过链表相连。一个页能容纳很多 key，树高通常很低，既适合等值查询，也适合范围、排序和前缀匹配。数据库以页为 I/O 单位，B+ 树的高扇出和叶子顺序访问与存储模型匹配，所以 InnoDB 主要使用 B+ 树。

钱包中除 `tx_hash` 等值查询外，还需按 `status + updated_at` 扫描超时任务、按 `chain + block_height` 重扫、按 `account_id + created_at` 查流水，B+ 树能统一支持。索引仍要按查询设计；过多索引会增加写放大，低选择性字段单独建索引也未必有效。

### 14. 主键与非主键和索引的关系

**完整回答：**

InnoDB 的主键索引是聚簇索引，叶子直接保存整行数据。一张表只有一种物理聚簇顺序。没有显式主键时，InnoDB 会选择合适的唯一非空索引；仍没有时会生成隐藏行 ID。

非主键索引通常是二级索引，叶子保存“二级索引列 + 主键值”。查询完整行时先找到主键，再回聚簇索引取其他列，这叫回表。所需字段都在二级索引中时可使用覆盖索引。组合索引遵循最左前缀，并受范围条件等因素影响。

主键会被每个二级索引携带，所以应稳定、短小、基本递增。资金业务表常用内部 ID 做主键，同时对真实业务键建唯一索引。例如提币表对 `tenant_id + client_request_id` 建唯一索引；不能因为已有自增主键就忽略业务幂等约束。

### 15. 进程、线程、协程的区别

**完整回答：**

进程是操作系统资源隔离和分配的基本单位，拥有独立虚拟地址空间；进程间通信需要管道、Socket、共享内存等，隔离强但创建和切换成本较高。

线程是进程内的执行单元，同一进程线程共享堆和文件句柄，但各有栈和程序计数器。线程由操作系统调度，通信方便，同时会带来数据竞争、死锁和切换成本。

协程是用户态或运行时管理的轻量任务，可在等待 I/O 时挂起并让出执行权。它比线程轻，但协程不自动等于并行；是否并行取决于运行时是否调度到多个 OS 线程。Go goroutine 通过 G-M-P 模型复用线程；Java 虚拟线程也是轻量并发单元，但两者语义并不完全相同。

进程适合故障和安全隔离，线程适合进程内并行，协程适合大量 I/O 并发。无论使用哪种模型，共享数据库和链资源仍需事务、唯一约束和明确并发控制。

### 16. Golang 协程间如何通信

**完整回答：**

Go 推荐通过 channel 在 goroutine 之间传递数据或同步信号，也可使用共享内存配合 `sync.Mutex`、`RWMutex`、`atomic`、`WaitGroup` 等工具。原则不是绝对禁止共享内存，而是根据所有权和访问模式选择清晰方式。

无缓冲 channel 的发送与接收会同步会合；有缓冲 channel 可在容量范围内解耦生产和消费。`select` 能等待多个 channel，常与 `context.Context` 结合实现取消、超时和优雅退出。channel 通常由发送方关闭；向已关闭 channel 发送或重复关闭会 panic，接收方可用第二个返回值判断是否关闭。

工程上要防止 goroutine 泄漏、永久阻塞和无界并发。节点 RPC worker 应使用有界队列、超时 context 和并发上限。channel 只协调单进程任务，不能代替数据库幂等；崩溃后需恢复的提币和扫链进度必须持久化。

### 17. 算法问题：判断链表是否有环

**完整回答：**

使用 Floyd 快慢指针。慢指针每次走一步，快指针每次走两步。无环时快指针或其 next 最终为 `null`；有环时快指针会在环内追上慢指针。时间复杂度 `O(n)`，空间复杂度 `O(1)`。

```java
boolean hasCycle(ListNode head) {
    ListNode slow = head;
    ListNode fast = head;

    while (fast != null && fast.next != null) {
        slow = slow.next;
        fast = fast.next.next;
        if (slow == fast) {
            return true;
        }
    }
    return false;
}
```

若追问环入口，首次相遇后将一个指针移回头节点，两个都每次走一步，再次相遇处就是入口。设头到入口为 $a$，入口到首次相遇为 $b$，环长为 $c$，快指针比慢指针多走整圈，可推导头到入口与相遇点继续绕到入口的距离在模环长下相等。

### 18. 堆排序、快速排序的时间复杂度以及适用场景

**完整回答：**

堆排序建堆是 `O(n)`，随后 `n` 次取堆顶和调整，每次 `O(log n)`，平均和最坏都是 `O(n log n)`；它可原地排序，额外空间 `O(1)`，但通常不稳定，缓存局部性较差。

快速排序平均 `O(n log n)`，最坏 `O(n²)`，递归栈平均 `O(log n)`。它通常原地且不稳定，但顺序访问和缓存局部性好，实践性能常优于堆排序。随机 pivot、三数取中、三路划分可降低退化风险；工程库常用 introsort，在递归过深时切换堆排序。

若要求稳定排序，考虑归并排序或 TimSort；若只要 Top K，可用大小为 K 的堆，将复杂度降到 `O(n log k)`。选择不能只看大 O，还要考虑稳定性、内存、数据分布、缓存和是否需要完整排序。

### 4. 为什么用区块链？区块链的创新点在哪

**完整回答：**

区块链的核心价值不是让数据库更快，而是在多个缺少统一可信中心的参与方之间，用共识、密码学和经济机制维护一份可共同验证的状态与资产所有权记录。

创新可以分四层：分布式共识解决参与方对交易顺序和状态的共同确认；数字签名让资产控制权由密钥证明，Merkle 结构让数据高效验证；原生 Token 和激励机制将网络安全与经济利益结合；智能合约把资产规则变成公开、确定执行的程序，形成可组合协议。

适合区块链的场景通常是多方协作但互不完全信任，需要公开验证、追溯和可编程资产。若只有一个可信运营方、要求高吞吐低延迟、数据强隐私且可随时修改，普通数据库往往更合适。交易所钱包中，链上用于所有权和结算，平台内部高频交易仍主要用中心化账本。

### 5. Web3 项目开发的技术难点

**完整回答：**

最难的不是调用链 SDK，而是处理不可逆外部系统与内部资金账本的一致性。

第一，链上状态存在 pending、确认、替换、丢弃、重组或异步部分执行，RPC 超时也不代表失败。系统必须表示“结果未知”，保存证据并恢复，不能盲目重试造成重复支付。

第二，多链差异大。BTC 是 UTXO 和找零，EVM 是 nonce 和 Gas，Solana 是 Blockhash、账户锁和 Instruction，TON 是 `seqno`、Cell 和异步消息。可以统一业务能力，不能抹平资源和失败语义。

第三，资金正确性需端到端设计。充值采用至少一次扫描、链上唯一键和幂等账本；提币采用请求幂等、冻结、资源预留、签名绑定和未知广播恢复；账本使用最小单位整数、不可变分录和对账。

第四，密钥与签名安全。HSM 或 MPC 只能降低密钥泄露风险，不能判断业务是否合理，所以签名服务要独立解析交易，核对地址、金额、资产、费用和审批，并配置热钱包水位、额度、白名单和紧急停签。

第五，节点、桥、RPC 和 AML 供应商会故障或返回冲突数据，需要多供应商、健康检查、限流熔断、证据留存和保守降级。难点是在业务可用与不可逆资金风险之间做正确取舍。

**完整回答：**

第一，引入 EVM 和表达能力更强的智能合约，开发者可部署长期存在并相互调用的程序。第二，采用账户模型和全局状态，合约可持有余额及复杂 storage，更自然地表达 DeFi、Token 和 DAO。第三，统一合约接口和 Event 机制催生 ERC-20、ERC-721 等标准，增强组合性。第四，Gas 为计算与存储定价，限制资源滥用并形成费用市场。
